# 岁记 权限模型简化方案 v1.3（创建者 / 成员 两角色）

| 项 | 内容 |
| --- | --- |
| 版本 | v1.3（权限模型修订稿） |
| 日期 | 2026-11-12 |
| 替代范围 | PRD v1.2 §6.2 / FR-18~21 / FT-28/30/31/32 / §11.1；TDD v3.0 §8；API-CONTRACT §4/§6 权限与只读相关条目 |
| 决策来源 | 产品拍板：**不再设计复杂权限，家庭内只区分创建者与成员；创建者无限制，成员只能修改、删除自己创建的记录，其余边界不再涉及** |

---

## 一、决策背景

现有实现与文档里叠了三层权限概念：

1. **角色**：`creator / member`（`family_member.role`）；
2. **家庭只读开关**：`family.readonly`，开启后全体非创建者只读（`PATCH /family/readonly`）；
3. **健康日志成员级可见性**：`health_visibility`（PRD 承诺，服务端未实现，客户端留有死代码）。

按新决策，第 2、3 层整体废弃，只保留第 1 层两角色，并把"成员可写范围"明确收敛到**本人创建的记录**。

> 本次只动权限模型，不改动记录类型、数据结构、同步方式等其他设计。

## 二、新权限模型

### 2.1 角色定义

| 角色 | 含义 | 数量约束 |
| --- | --- | --- |
| **创建者 `creator`** | 家庭空间的所有者，拥有全部权限 | 家庭唯一；创建者离开时按现有规则自动交接给最早加入的成员 |
| **成员 `member`** | 被邀请加入的家人，可参与记录，仅能处置本人创建的记录 | 不限人数 |

### 2.2 能力矩阵（新口径）

| 能力 | 创建者 creator | 成员 member |
| --- | --- | --- |
| 浏览全家档案、记录、健康日志、相册、动态、留痕 | ✅ | ✅ |
| 新增记录（喂养/睡眠/测量/里程碑/照片/语音/视频等） | ✅ | ✅ |
| 修改记录 | ✅ 任意记录 | ✅ **仅 `creator_id == 本人` 的记录** |
| 删除 / 恢复 / 彻底删除记录 | ✅ 任意记录 | ✅ **仅 `creator_id == 本人` 的记录** |
| 上传 / 删除记录附件（照片、视频、语音） | ✅ | ✅ 跟随记录归属：本人记录上的附件可改/删（见 §4.5） |
| 维护个人设置（音效、震动、个人偏好等） | ✅ | ✅ |
| 建档 / 改宝宝档案 / 切换当前宝宝 | ✅ | ✅ 成员可参与（决策 1：不收口创建者，见 §7.1） |
| 邀请成员、转让创建者、移除成员 | ✅ | ❌ |
| 清空回收站（批量彻底删除） | ✅ | ❌（家庭级动作） |
| 导入覆盖家庭数据 | ✅ | ❌ |
| 清空家庭全部数据 | ✅ | ❌ |
| 导出家庭副本 / 导出留痕上报 | ✅ | ❌ |

**明确不再做的边界**（原 PRD 承诺，本次废弃）：

- ~~家庭只读开关~~：不再有"全体成员临时只读"状态；
- ~~健康日志成员级可见性裁剪~~：健康日志对全家成员可见，不做按人开关；
- ~~第三/第四角色、只读亲友、管理员~~：不存在；
- ~~按字段/按记录类型的细粒度授权~~：不做。

### 2.3 归属判定规则（服务端唯一权威口径）

记录归属以 `entry.creator_id`（用户 ID，令牌解析所得）为准，**不采信客户端传入的 creator 名字串**。

- 创建者：`auth.role == "creator"` → 放行任意记录；
- 成员：`entry.creator_id == auth.user_id` → 放行；否则 `403`；
- 历史无主记录（`creator_id == ""`）：成员不可改删，仅创建者可处置（保守口径，避免把老数据误判给某个成员）。

## 四、服务端改造方案

### 4.1 鉴权依赖层级（重构后）

```
get_auth            校验 JWT 签名 / 类型 / 撤销账本 → AuthContext
  └─ require_family        已加入家庭，否则 409 need_family
       └─ require_member    普通写操作放行（替代原 require_write 的家庭门控）
            └─ require_creator  家庭级管理动作，仅 creator
```

- **`require_member(auth)`**：登录 + 已入家庭即放行，用于新增记录、个人设置、附件上传等成员可参与的写操作；不再有 readonly 拦截。
- **`require_creator(auth)`**：`auth.role != "creator"` → 403，用于家庭级管理动作。
- 记录级归属**不放在依赖注入里**（依赖拿不到具体记录），统一在 service 层用归属函数判定。

### 4.2 归属校验函数（新增，service 层复用）

在 `services/entry_service.py`（或 `core/deps.py`）新增：

```python
from fastapi import HTTPException

def assert_entry_writable(auth: AuthContext, entry) -> None:
    """记录改/删/恢复/彻底删除前的归属校验。

    creator 任意记录；member 仅本人创建；历史无主记录 member 不可处置。
    """
    if auth.role == "creator":
        return
    if entry.creator_id and entry.creator_id == auth.user_id:
        return
    raise HTTPException(status_code=403, detail="只能修改或删除自己创建的记录")
```

调用点：`update_entry` / `soft_delete` / `restore` / `purge_entry` 前置；`purge` 端点（`entries.py:76`）在 `scoped_get` 之后同样调用。

### 4.4 读路径

- 所有 `GET` 端点维持 `get_auth` / `require_family` 家庭隔离即可；**不再按角色或可见性开关过滤健康日志**。
- 跨家庭访问仍由 `scoped_get` / `family_id` 条件拦截，返回 403/404，口径不变。

### 4.5 附件删除归属（跟随记录）

- 附件归属**跟随其所属记录**，不按上传人 `uploader_id` 判定（决策 3）。
- 校验规则：`auth.role == "creator"` 放行；成员仅可改/删本人创建记录上的附件：
  - `business_type=entry`：按挂载 `entry.creator_id` 校验；
  - `business_type=entry_media`：反查 `EntryMedia.entry_id` 对应记录后校验；
  - `business_type=baby`：宝宝档案资料，随档案可写，不做个人归属；
  - `other/空` 等未挂具体记录的附件：成员不可处置。
- 所属记录为无主历史记录（`creator_id=""`）时，成员不可操作。
- 记录被 creator/本人删除时，连带清理挂载附件的现有逻辑（`purge_entry`）保持不变。
- `uploader_id` 仍记录上传人用于留痕，但不作为改删归属依据。

### 4.5.1 派生数据的归属字段现状（复核 2026-11-12）

| 派生数据 | 归属字段现状 | 问题 |
| --- | --- | --- |
| 里程碑 `milestone_record` | 有 `creator`（名字串），无 `creator_id`；`PUT /milestones/{id}` 的 `_PATCH_FIELDS` 含 `creator` | 客户端可改写归属人；无法按用户 ID 做可靠归属校验 |
| 日记 `ai_journal` | **无任何创建人字段** | 成员可改家庭内任意草稿，无归属概念；需先决策是否补 `creator_id` |
| 疫苗 `vaccine` | **无创建人字段** | 打卡/改排期无归属；按 §7.2 决策收口 creator 或补字段 |

> 若选择"成员可写但按本人校验"，里程碑需补 `creator_id` 列并把 `creator` 移出可写白名单；日记、疫苗同理补字段。若选择"收口创建者"，则不补字段，端点改 `require_creator`。

**落地结论（2026-11-12）**：里程碑、日记已补 `creator_id` 并按本人校验（里程碑 `creator` 已移出可写白名单）；疫苗不补字段，保持家庭共享、成员可写。

## 五、客户端改造方案

1. **权限判定下沉到单条记录**：编辑/删除按钮显隐条件改为 `isCreator || entry.creator_id === currentUserId`；他人记录不展示编辑、删除、彻底删除入口。
2. **删除全局只读拦截**：移除 `readOnly()` 及其在保存/编辑/删除前的 reject；服务端 403 作为兜底。
3. **移除只读开关 UI**：「我的」页开关区块、家庭页只读描述、成员三态徽标（editor/viewer）全部清理，只保留 创建者 / 成员 两态。
4. **角色文案**：
   - 创建者："创建家庭空间 · 全部权限"；
   - 成员："可记录 · 仅能修改和删除自己的记录"。
5. **403 提示文案**：由"当前是只读模式，暂时不能修改"改为"只能修改或删除自己创建的记录"（他人记录场景）/"仅创建者可操作"（家庭级动作场景）。
6. **删除死代码**：`getHealthVisibility` / `setHealthVisibility` 及相关设置入口。
7. **当前用户 ID 来源**：客户端从登录态 / bootstrap 成员信息取本人 `user_id`，用于前端归属显隐；最终判定以服务端为准。

## 七、待产品确认的边界

> **落地口径（2026-11-12，已拍板并实现，见 §9.5）**：7.1 宝宝档案**不收口创建者**，成员可参与建档/改档/切换；7.2 里程碑、日记补 `creator_id` 按本人校验，疫苗按家庭共享排期保持成员可写、不做个人归属；7.3 附件**跟随记录归属**判定。

### 7.1 宝宝档案操作（决策：成员可写，不收口创建者）

建档、改档案（昵称/生日/胎周/性别等）、切换当前宝宝，成员均可操作；三端点走 `require_member`，家庭隔离仍由 `scoped_get` 保证跨家庭 403。

### 7.2 疫苗 / 里程碑 / 日记的写归属（默认建议：成员可写）

- 里程碑记录自带 `creator`，按归属校验；
- 疫苗排期勾选、日记生成/编辑默认放行成员（视为参与照护的派生记录）。
- 若严格按"成员只能动自己的记录"，可把疫苗同步/勾选也收口创建者；需产品确认。

### 7.3 附件删除粒度（决策：跟随记录归属）

附件随所属记录走：记录本人（或创建者）可处置其全部附件；不按上传人 `uploader_id` 判定。宝宝头像等档案资料随档案可写；未挂具体记录的附件成员不可处置。

## 八、测试与验收口径

**服务端用例（新增/调整）**

1. 创建者改/删/恢复/彻底删除任意成员记录 → 200。
2. 成员改/删/恢复/彻底删除本人记录 → 200。
3. 成员改/删/恢复/彻底删除他人记录 → 403，且数据未被改动。
4. 成员操作无主历史记录（`creator_id=""`）→ 403；创建者 → 200。
5. 成员调用清空回收站 / 导入覆盖 / 清空全家 / 邀请 / 转让 / 移除成员 → 403。
6. 成员新增记录、上传附件、改个人设置、生成/编辑日记草稿 → 200。
7. 跨家庭访问任意记录仍 403/404（回归现有隔离用例）。

**回归项**

- 现有服务端用例中，涉及 `readonly` 的断言已同步改写；最终全量 **120 passed**（见 §9.5）；
- 客户端主流程：成员账号下他人记录不出现编辑/删除入口；本人记录可正常编辑删除。

**验收标准**

- 代码与契约中不再存在只读开关、健康可见性两套概念；
- 记录改删路径服务端有归属校验，前端显隐与服务端判定一致；
- PRD/TDD/契约文档表述与本方案一致，无残留"只读开关/可见性配置"字样。
